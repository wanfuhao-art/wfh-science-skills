# 整稿交付检查（保留原自检文件路径）

> 在 `integrate`、最终稿或用户要求交付检查时读取。专业核验由实际 ARS 契约负责，本文件只定义 wfh 的交付责任。

## 1. 职责

ARS 执行引用、方法、实验来源、完整性等专业检查；具体规则和适用性读取当前模式原文。wfh 读取其实际产物和报告，核对当前交付目标与研究方案的衔接。过去的 M1–M7 自检不再作为另一套专业门禁维护；旧记录原样保留，不能自动换算成 ARS 通过。

独立引用核对、局部修改等小任务按自己的标准验收，不附加整稿检查或强制启动全流程。

## 2. 交付核对

| 核对项 | 要读取的依据 | 缺口处理 |
|---|---|---|
| 目标与范围 | 用户约定目标、相关任务标准、实际文件与章节 | 缺产物或超范围改动记未完成，不修改标准迁就结果 |
| 产物与来源 | 实际版本、数据 / 文献 / 方法来源指针、ARS 调用与产出记录 | 来源缺失明确列出；不以文件存在代替真实执行 |
| 专业检查状态 | 当前模式要求的报告、原生结论及其绑定版本 | 分清已执行、未执行、不适用和无法判断；必需检查缺失或不通过则保留阻塞 |
| 研究一致性与交接 | 已确认问题、主张边界、术语、意见回应及未决项 | 实质性变化提交作者决定；记录需补证或重开范围 |

本表检查记录与可见内容是否一致；出现明确矛盾时展示证据，不以 ARS 自称通过忽略矛盾，也不另跑同一套专业检查冒充独立验证。

## 3. 记录

在目标任务的验收表或独立请求的交付说明中记录：

`核对项 | 适用性及理由 | pass / fail / unresolved / not-applicable | 证据文件与版本 | 缺件与解决者`

- 只对适用项作 pass 判定。不适用必须给出研究类型或当前目标依据，不能用于掩盖缺失必需检查。
- 原生检查状态单独保留原文；本次模式没有运行某项检查，就记未执行，不能推断通过或自动要求整套 pipeline。
- 用户或当前契约明确要求专业核验时，缺报告即未完成；先安排真实检查，验收本身不补做生产。
- 交付完成与科学支持程度分开。研究可以诚实得到否定结果；是否完成以原标准判断，改变解释或后续研究方案由作者确认。
- wfh 的验收只表示当前约定工作已交付，不颁发 ARS PASS / VERIFIED 或研究有效性证明。

## 4. 原生完整性门禁

整稿确实进入 `academic-pipeline` 时，按当前 ARS 契约运行 Stage 2.5 / 4.5 并读取实际结果；此前报告的复用、版本绑定和再次执行要求也由 ARS 决定。单技能调用不自动拥有 pipeline 的检查覆盖；报告实际检查范围即可。
