# 任务文件模板与切分规则（tasks/T*.md）

> wfh-research 共享包 · 2026-11-13
> 位置：`research/<slug>/tasks/T01-<slug>.md`
> 上游：`BRIEF.md`（claim ledger / 未决问题 / 待核验事实）、`TERMS.md`、`decisions/`
> 下游：执行会话（`wfh-next` 生成启动提示词）、`wfh-close` 按验收标准校验
> 原则：**一条任务 = 一个最小可验证主张单元；一个会话可完成；独立可验证。**

---

## 1. 这份文件是什么

任务文件既是**执行计划**，也是**执行记录**。开始时写计划（六层骨架 + 验收标准），执行中填证据 / 分析 / 图表 / 正文 / 引用，结束时写结论与完成记录。

| 写 | 不写 |
|---|---|
| 一条可证伪的任务主张 | 多条主张混在一起 |
| 证据清单与来源 | 原始数据全文（放 `tasks/assets/T<nn>/`） |
| 分析方法与判定规则 | 未定义的「进一步分析」 |
| 图 / 表 ID 与图注草稿 | 成品图的所有中间版本 |
| 目标章节与字数 | 整篇论文 |
| 引用键与核验状态 | 编造的引用 |
| 验收标准 | 主观的「写得好」 |

判断标准：**另一个会话只读这个文件 + 产出 + `BRIEF.md` 的对应 claim 行，能不能判断「这条主张站得住吗」？** 能，就够；不能，补字段或拆任务，不是补正文。

## 2. 任务类型

| 类型 | 用途 | 任务主张 | 典型执行方式 |
|---|---|---|---|
| `claim` | 论文主张的纵向切片 | 直接对应 `BRIEF.md` 的 `C#` | `direct` / `ARS` / `human` |
| `prep` | 共享证据基础、决策、测量、检索 | 支撑性主张（数据可用 / 测量可信 / 决策已定） | `direct` / `ARS` / `human` |
| `ec` | 全局机械改动的一个阶段 | 形式一致性主张（新形式可用 / 迁移完成 / 旧形式删除） | `direct` / `ARS:academic-paper:format-convert` |
| `integrate` | 把任务产出合并成一份稿（阶段 5 / 7 终端） | 整合一致性主张（每条 claim 有段落 / 术语一致 / 引用键齐全） | `ARS:academic-paper:full` / `direct` |
| `revision` | 阶段 7 的单条审稿意见簇 | 回应主张（意见被逐条回应 / 正文已改 / response 条目已写） | `direct` / `ARS:academic-paper:revision` / `human` |

- `claim` 是默认类型。每条 claim 至少一个任务；可以拆成多个，但不能跨 claim 合并。
- `prep` 只在被 **≥2 条** claim 任务消费时单独成任务；只被一条消费 → 并入那条 claim 任务。
- `ec` 只用于全局机械改动：术语替换、引用格式切换、时态统一、单位统一、缩写首次出现规则。内容改动不得走 `ec`。
- `integrate` 是终端任务：阶段 5 依赖所有 claim / prep / ec 任务，阶段 7 依赖所有 revision 任务；不新增 claim。
- `revision` 按审稿意见簇切，一条簇一个任务；编号 `R01` 起，不与 `T` 混号。
- 五种类型都必须是**纵向切片**：有自己的主张、证据、分析、图 / 表、正文、引用六层。`prep` / `ec` / `integrate` / `revision` 的「正文」可以是 Methods 数据段、受影响段落清单、合并记录或 response 条目，不是整篇论文。

## 3. 执行方式

| 值 | 含义 | 例子 | 硬规则 |
|---|---|---|---|
| `direct` | 当前会话直接完成 | 分析数据、画图、写一节 | 必须写清分析方法和判定规则 |
| `ARS:<skill>:<mode>` | 调 ARS 的某个技能与模式 | `ARS:deep-research:lit-review`、`ARS:academic-paper:citation-check`、`ARS:academic-paper-reviewer:full`、`ARS:academic-paper:format-convert` | 必须写全 skill 与 mode；ARS 不可用 → `ARS_NOT_AVAILABLE`，任务保持阻塞，不静默降级为 `direct` |
| `human` | 必须由人完成 | XPS / ICP-MS / SEM 机时、IRB、用户裁决、作者顺序 | 必须写：人工动作、返回物、核验方式、失败时怎么办 |

- 一条任务只有一个**主执行方式**；需要 ARS 辅助时，在「输入」或「分析」里写 `辅助调用: ARS:...`，不写成两个主执行方式。
- `human` 任务不得由会话代做；会话只做样品 / 机时准备、数据接收、QC 与后续分析。
- `ARS` 任务不得由会话凭记忆代替；必须实际调用对应技能，或在 `ARS_NOT_AVAILABLE` 时停下。

## 4. 六层纵向切片

| 层 | 必须回答 | 产出 | 验收 |
|---|---|---|---|
| 1 主张 | 这条任务要回答哪一句可证伪的话？ | 一句任务主张 + 对应 `C#` / 支撑关系 | 与 `BRIEF.md` 的 claim 措辞一致；强度不升级 |
| 2 证据 | 凭什么？ | 证据清单：来源 / 状态 / 存放路径 | 每条可追溯；`[待核验]` 原样保留 |
| 3 分析 | 怎么从证据走到主张？ | 方法、判定规则、不确定性、替代解释 | 判定规则在分析前写；可复现 |
| 4 图 / 表 | 读者看什么？ | 图 / 表 ID、数据源、图注草稿、一句话结论 | 一图一结论；数据可追溯 |
| 5 正文 | 写哪一段？ | 目标章节、字数、claim 强度、边界句 | 不超出证据强度；不写「进一步研究」 |
| 6 引用 | 依据哪些文献？ | 引用键 + `[待核验]` 标记 + 来源 | 不编造；本任务只登记键与状态，全局核验由 §6.12 的终端任务做 |

- 六层缺一不可。缺哪层就说明任务没切好：回到 §6 重新切，不要用「后续补」占位。
- `claim` 任务不要求逐条核验引用；把引用键、来源与 `[待核验]` 写清即可。全局核验见 §6.12。
- `prep` 的第 1 层是支撑性主张；第 5 层通常是 Methods 数据段或测量记录；第 6 层是数据 / 仪器溯源。
- `ec` 的第 1 层是形式一致性主张；第 3 层是迁移批次；第 4 层是 before / after 对照表；第 5 层是受影响段落清单；第 6 层是格式规则与核验记录。
- `integrate` / `revision` 的第 6 层登记引用键与 response 条目的对应关系；不改 claim。

## 5. 字段规范

### 5.1 Task ID 与文件名

- `T01`–`T99`，两位递增；不复用，不重排，不删除。
- 文件名：`tasks/T<nn>-<kebab-slug>.md`；slug 用英文小写短横线，≤ 40 字符。
- 新任务追加最大编号；被取消的任务保留文件，状态标 `dropped`，在完成记录写原因。
- `ec` 任务文件名带阶段：`T13-ec-expand-citation-format.md`、`T14-ec-migrate-citation-format.md`、`T15-ec-contract-citation-format.md`。

### 5.2 状态

| 状态 | 含义 |
|---|---|
| `todo` | 未开始；blockers 可能未完成 |
| `doing` | 当前会话正在做 |
| `done` | 验收标准全部满足，结论已写 |
| `blocked` | blockers 未完成，或 `ARS_NOT_AVAILABLE` / 人工资源未到位 |
| `dropped` | 用户确认取消；保留文件与原因 |

- 状态只由执行会话或 `wfh-close` 改；不改别人的任务状态。
- 状态与 `FLOW.md` 的任务行必须一致；冲突先报原值并停写，只有用户明确授权按已核验事实源同步时才修 FLOW，见 state_protocol §2。

### 5.3 对应主张 / 子问题

- `claim`：写 `C#` + 主张原文（照录 `BRIEF.md`，不改写）。
- `prep`：写 `—（支撑 C#、C#）`，并在任务主张里写支撑关系。
- `ec`：写 `—（全局机械改动）`。
- 对应子问题写 `SQ#`；一条任务可对应多个子问题，但必须有至少一个。

### 5.4 Blocked by

- `—`：无前置任务，可立即执行。
- `T01, T02`：全部完成才可开始；不做「部分完成即可开始」。
- 不得引用不存在的任务；不得形成环；不得用「等数据」这种模糊 blocker。
- 前置是人工任务时，写清人工返回物；前置是 ARS 任务时，写清 ARS 产出。
- 全局机械改动的 `ec` 组：`expand` 阻塞 `migrate`，`migrate` 阻塞 `contract`；`contract` 还要等所有可能引入旧形式的正文任务完成。

### 5.5 执行方式

见 §3。写全 `ARS:<skill>:<mode>`，不写「用 ARS」。

### 5.6 输入

- 列出本任务要读的文件，精确到路径：`BRIEF.md`、`TERMS.md`、`decisions/MDR-xxxx.md`、`tasks/T01-....md`、数据文件。
- 只列本任务需要的；不写「读全部」。
- 输入不存在 → 任务不能开始；标 `blocked` 并写缺什么。

### 5.7 产出路径

- 任务文件本身是六层记录：`tasks/T<nn>-<slug>.md`。
- 附件放 `tasks/assets/T<nn>/`：图 `F-<claim>-<nn>-<slug>.png`、表 `TB-<claim>-<nn>-<slug>.md`、原始数据 `raw/`、日志 `logs/`、分析脚本 `analysis/`。
- `artifacts/` 只放 ARS Schema 2–8 产物；任务工作产物不写 `artifacts/`。
- 默认产出路径唯一。ec 分批迁移、revision 和终端 integrate 可串行更新同一稿件或回复文件，但必须声明负责的精确段落／条目、前后证据和顺序；有重叠的写入以依赖边串行化，不并行覆盖。

### 5.8 验收标准

- 二元可判：存在 / 不存在、齐全 / 不齐全、通过 / 不通过。
- 至少覆盖：
  1. 产出存在且六层齐全；
  2. 证据可追溯（来源 / 状态 / 存放）；
  3. 分析可复现（方法 / 判定规则 / 不确定性）；
  4. 图 / 表有数据源与图注；
  5. 正文与 claim 强度一致，无过度断言；
  6. 引用可核验，无编造；
  7. 结论用四选一 token（`站得住` / `部分站得住` / `站不住` / `证据不足`）；
  8. 独立验证者只读本文件 + 产出 + `BRIEF.md` 对应行即可判断。
- 不写「写得好」「分析充分」这类主观标准。
- `prep` / `ec` 的验收标准按支撑性主张改写，但 1–4、6–8 仍适用。

### 5.9 会话预算

| 预算 | 上限 | 产出 |
|---|---|---|
| `S` | ≤30 分钟；必读输入 ≤4 文件 | 1 份记录（无图或 1 小表） |
| `M` | ≤90 分钟；必读输入 ≤6 文件 | 1 份记录 + 1 图 / 表 |
| `L` | ≤1 个会话（硬上限约 2 小时）；输入按任务需要；必须写拆分工序 | 1 份记录 + 多图表（仍可独立验证） |

- `human` 任务：写 `S` / `M` 指 AI 会话的准备与核验时间；人工机时另计，写在「人工动作」里。
- 预算不是承诺，是切分依据；执行中发现超预算 → 停下，按 §6.2 拆分，不硬撑。

### 5.10 独立验证

- 写一句：验证者只需读哪些文件。
- 默认：`本文件` + `tasks/assets/T<nn>/` + `BRIEF.md` 的对应 claim 行。
- 不得要求验证者读盘问对话、全部 MDR 或整篇论文。

### 5.11 风险与未决

- 风险写具体失效模式：样本量不足、仪器检出限、批次差异、对照不可比、编码主观性。
- 未决项写 `[UNRESOLVED]` + 为什么 + 谁能解决 + 影响哪个验收标准。
- 待核验写 `[待核验]` + 已查来源 + 为什么没查到。
- 不得把未决项藏在正文里；必须在 `FLOW.md` 的未决问题区有对应行。

### 5.12 完成记录

- 每次执行追加一行：日期 / 会话标识 / 做了什么 / 验收结果 / 遗留。
- 不改历史行；修订用追加。
- `done` 必须有完成记录；`dropped` 必须写原因。

## 6. 切分与建图规则

### 6.1 一主张一任务（默认）

- `BRIEF.md` 的每条 claim 至少一个 `claim` 任务。
- 任务主张照录 claim；不改写、不加强、不弱化。
- 一条 claim 拆成多个任务时，每个任务只负责 claim 的一个可独立验证的部分；在任务主张里写「C2 的 CEI 部分」这种限定。

### 6.2 何时拆

- 证据来源可独立失败：循环数据、XPS、ICP-MS、SEM 分开。
- 一张图 / 表一个任务：多个图 → 拆。
- 人工测量与分析分开：`human` 测量 → `direct` 分析。
- 预估超过 `L` → 按层或按批次拆。
- 一条任务出现两个「这条主张站得住吗」的答案 → 拆。

### 6.3 何时合

- 只在同一 claim 内合。
- 合并后仍 ≤ `M`，且一套验收标准能覆盖。
- 不跨 claim 合并；不把 `human` 与 `direct` 合成一个主执行方式。
- 合并不是默认；用户确认门可以要求合并。

### 6.4 预加工任务（`prep`）

- 适用：共享数据清洗、文献检索、量表核对、IRB / 知情同意、仪器预约、样本制备、倍率 / 电压等前置决策。
- 只在被 ≥2 条 claim 任务消费时单独成任务；只被一条消费 → 并入那条 claim 任务。
- 例外：`human` 测量 / 仪器任务即使只被一条 claim 消费，也单独成任务（执行方式不同，不能并进 `direct` 分析任务）。
- 必须有支撑性主张与可验证产出；不能是「先准备一下」。
- 预加工任务通常放在主张链之前；与 T01 无关的 `prep` 可并行，T01 需要的 `prep` 并入 T01 的证据层，或先补 `prep` 再重选 tracer bullet。

### 6.5 人工任务（`human`）

- 适用：湿实验、仪器机时、外部数据获取、用户裁决（FINER、作者顺序、期刊选择）、伦理审批。
- 必须写：
  - **人工动作**：谁、做什么、用什么仪器 / 流程；
  - **返回物**：原始数据、谱图、日志、签字 / 确认；
  - **核验方式**：会话如何检查返回物（校准、空白、检出限、样本追溯）；
  - **失败时**：重测、换方法、降级为 `[UNRESOLVED]` 或停止。
- 会话不得替人做测量或裁决；不得编造人工结果。
- 人工任务可以与其他任务并行；在 `FLOW.md` 里标 `blocked` 直到返回物到位。

### 6.6 ARS 任务

- 适用：文献检索（`ARS:deep-research:lit-review`）、事实核验（`ARS:deep-research:fact-check`）、筛选（`ARS:sr-screener:*`）、审稿（`ARS:academic-paper-reviewer:*`）、格式转换（`ARS:academic-paper:format-convert`）、引用核验（`ARS:academic-paper:citation-check`）。
- 必须写全 `ARS:<skill>:<mode>`；不写「用 ARS 查一下」。
- ARS 产出要落到任务文件或 `tasks/assets/T<nn>/`；不把 ARS 对话当产出。
- ARS 不可用 → `ARS_NOT_AVAILABLE`；任务保持 `blocked`，不降级为 `direct`。

### 6.7 未决项映射

- `BRIEF.md` 的每个 `[UNRESOLVED]` 必须二选一：
  1. 转成 `prep` / `human` 决策任务，阻塞受影响的 claim 任务；
  2. 在受影响的 claim 任务里写成显式假设 + 降级规则（「若未决，结论只能到『证据不足』」）。
- 不得静默忽略；不得在任务里替用户定值。
- `[待核验]` 必须落到一个任务的「引用」或「证据」层，写明谁核验、核验不通过怎么办。
- `FLOW.md` 的「未决问题」区必须有对应行，写消费任务。

### 6.8 Tracer bullet（T01）

- T01 必须是 `claim` 类型，六层完整，`Blocked by: —`，一个会话可完成。
- T01 的输入必须现成；若关键数据不存在，T01 标 `blocked`，先补 `prep` 任务，不硬造 tracer bullet。
- 选择标准：证据最现成、分析最简单、最能代表论文主张链的那条 claim。
- T01 的产出是后续任务的样板：六层结构、图 / 表样式、引用键格式、正文字数。
- T01 的验收标准必须包含「用户确认 T01 可作为后续任务样板」。
- 若没有任何 claim 能在一个会话内跑通 → 不硬造 T01；停下来，先补 `prep` 或请用户解决阻塞项，再切任务。
- T01 不一定是唯一 frontier；其他无 blocker 的任务可以并行准备（如人工测量、文献检索），但后续 `claim` 任务在 T01 样板确认前不写正文，只做证据准备。

### 6.9 Expand–contract（全局机械改动）

- 适用：术语替换、引用格式切换、时态统一、单位统一、缩写首次出现规则。
- 不适用：内容改写、论证调整、新增主张、数据重分析。
- 三个阶段，每个阶段一个 `ec` 任务：

  1. **`expand`**：新形式与旧形式并存；建映射表；选一个试点章节；旧形式不动。
  2. **`migrate`**：按章节 / 批次迁移；每批只改形式，不改内容；每批有 before / after 计数与回滚点。
  3. **`contract`**：删除旧形式；全量扫描；核验零残留；更新映射表状态。

- 依赖：`expand` → `migrate` → `contract`；`contract` 还要等所有可能引入旧形式的正文任务完成。
- 每批迁移后跑一次引用 / 格式核验；失败则回滚该批，不进入下一批。
- 若成稿整合（阶段 5）发生在 `ec` 之后，成稿后要再跑一次 `contract` 扫描；或让成稿整合直接使用新格式，避免旧形式回流。
- `ec` 任务不得顺带改内容；发现内容问题 → 新开 `claim` 任务，不塞进 `ec`。

### 6.10 无环与拓扑序

- 任务图是有向无环图；边 = `blocked by`。
- 落盘前做一次拓扑排序：每次取走「所有 blockers 已完成」的任务；取不完 → 有环，报 `TASK_GRAPH_CYCLE`，列出环上的任务，停。
- Task ID 按拓扑序分配：T01 最先，后续尽量前置依赖在前；允许并行分支。
- 新建时编号尽量按拓扑序；增量添加前置可能出现后号阻塞前号，仍以实际依赖图的拓扑排序检查，不重排旧编号，不为编号顺序篡改依赖。
- 不允许自环、重复边、引用不存在的任务。

### 6.11 会话预算与独立性

- 每条任务 ≤ `L`；超过 → 拆。
- 每条任务独立验证：验证者只读任务文件 + 产出 + `BRIEF.md` 对应 claim 行。
- 每条任务一个主执行方式；混合执行方式 → 拆。
- 每条任务一个明确的「这条主张站得住吗」答案；答案需要两个 → 拆。

### 6.12 引用核验任务（`prep` 或终端）

- 触发：claim 任务共享文献、同一文献跨 claim 复用、或需要统一引用格式。
- 执行方式：`ARS:academic-paper:citation-check`。
- 输入：所有 claim 任务的引用键 + `artifacts/02-bibliography.md`。
- 产出：`tasks/assets/T<nn>/citation-report.md`（逐条：键 / 来源 / 核验结果 / 修正）。
- 依赖：所有产生引用键的 claim 任务完成；通常放在终端 `integrate` 之前。
- claim 任务只登记引用键与 `[待核验]`，不各自跑核验；避免同一文献重复核验、格式不一致。

### 6.13 revision 任务切分（阶段 7）

- 输入：审稿意见（`artifacts/06-review-report.md` 或用户提供的审稿信）。
- 切分单位：**一条意见簇** = 一个可独立回应的关注点；同一段落的多条意见可合成一簇，跨章节的同一问题不拆。
- 每条 `revision` 任务必须写：
  - 意见簇原文（逐条照录）；
  - 回应策略（改正文 / 补分析 / 解释不改 / 降级主张）；
  - 受影响章节与 claim；
  - 验收：意见被逐条回应 + 正文已改 + response 条目已写。
- 编号 `R01` 起；`Blocked by` 可指向 `T` 或 `R`。
- 终端 `integrate` 任务在 revision 之后复检全文一致性。
- 改 claim 本身 → 回 `wfh-spec` / `wfh-grill`；`revision` 任务不改 claim。

### 6.14 终端 integrate 任务（阶段 5 / 7）

- 阶段 5：依赖所有 claim / prep / ec 任务；阶段 7：依赖所有 revision 任务。
- 执行方式：`ARS:academic-paper:full`（有 BRIEF + 任务产出时）或 `direct`（已有草稿，只做合并与一致性检查）。
- 输入：`BRIEF.md`、`TERMS.md`、所有任务文件与 `tasks/assets/`。
- 产出：`artifacts/05-draft.md`（阶段 5）或更新后的 `artifacts/05-draft.md` + `artifacts/09-response.md`（阶段 7）。
- 验收：
  - 每条 claim 在正文有对应段落；
  - 术语与 `TERMS.md` 一致；
  - 引用键齐全，无 `[citation]` 占位；
  - 不新增 claim、不改主张强度；
  - 阶段 7 还要求每条审稿意见有 response 条目。
- `integrate` 不替代 `wfh-close`；由 close 逐条验收。

## 7. 写法规则

### 7.1 任务主张

- 一句可证伪的话；不写「研究一下」「分析一下」。
- `claim` 任务照录 `BRIEF.md` 的 claim；不改写。
- `prep` 任务写支撑性主张：数据可用、测量可信、决策已定、检索可复现。
- `ec` 任务写形式一致性主张：新形式可用、迁移完成、旧形式删除。
- 主张强度与 `BRIEF.md` 的 D04 一致；BRIEF 是关联，任务不能写因果。

### 7.2 证据

- 每条证据写：来源、状态（已有 / 待采集 / 待核验 / 待分析）、存放路径。
- 原始数据不入正文；放 `tasks/assets/T<nn>/raw/`，在任务文件里写路径。
- `[待核验]` 原样保留；核验后改成具体来源，并在完成记录留痕。
- 不得把文献结论写成自己的数据；不得把 `[待核验]` 写成确定结论。

### 7.3 分析

- 先写判定规则，再跑分析：什么结果算支持、什么算不支持、什么算证据不足。
- 写清不确定性：样本量、重复数、误差线、检出限、编码者一致性。
- 写清替代解释：至少一个；不能排除就写「不能排除」。
- 不写「进一步研究」「深入分析」；要么现在做，要么新开任务。

### 7.4 图 / 表

- 一图一结论；图注草稿写清「展示什么、N 是多少、误差线是什么」。
- 图 / 表 ID：`F-C1-01`、`TB-C1-01`；同一 claim 内递增。
- 数据源写到文件路径；图由脚本 / 工具生成时，脚本放 `tasks/assets/T<nn>/analysis/`。
- 不把多个 claim 的图塞进一个任务；不重复使用同一图。

### 7.5 正文

- 写目标章节、字数范围、claim 强度、边界句。
- 一段只服务一条 claim；不在一段里塞多条主张。
- 不写超出证据的机制断言；不写「首次」「显著优于」除非证据支持。
- 引用占位用引用键，不用「[citation]」；引用键来自 `artifacts/02-bibliography.md` 或任务内的文献记录。

### 7.6 引用

- 每条引用写：引用键、来源、状态（`[待核验]` / 已由核验任务确认）。
- 不编造；查不到就 `[待核验]`，并写已查来源。
- claim 任务只登记引用键与状态，不各自跑核验；全局核验由 §6.12 的 `citation-check` 任务集中做。
- 引用格式由全局 `ec` 任务统一；单个任务不擅自切换格式。

### 7.7 验收标准

- 见 §5.8；每条标准二元可判。
- 至少一条标准直接回答「这条主张站得住吗」。
- 至少一条标准检查「没有过度断言」。
- 至少一条标准检查「引用无编造」。

### 7.8 结论

- 四选一：`站得住` / `部分站得住` / `站不住` / `证据不足`。
- 写理由：哪些证据支持、哪些不支持、哪些没排除。
- 写下一步：补证据、改主张、降级、或停止。
- 结论不改 `BRIEF.md`；若结论要求改 claim，回到 `wfh-spec` 修订 Brief。

## 9. 维护规则

1. **追加不覆盖。** 完成记录只追加；任务主张 / 验收标准变更要写原因。
2. **不改 `BRIEF.md`。** 任务发现问题 → 回 `wfh-spec`；不在这里改 claim。
3. **不改上游。** `TERMS.md` / `LEDGER.md` / MDR 只读；需要新决策 → `wfh-grill` 或 human 决策任务。
4. **不删除任务。** 取消标 `dropped`，保留文件与原因。
5. **编号不复用。** 新 `T` 任务用最大编号 +1；`revision` 任务用 `R` 前缀，从 `R01` 起；两类编号都不复用。
6. **不膨胀。** 任务文件超过约 150 行 → 检查是否把正文 / 综述搬进来了；拆任务或把细节放 `tasks/assets/`。
