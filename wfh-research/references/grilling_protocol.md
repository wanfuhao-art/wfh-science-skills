# 盘问协议（Grilling Protocol）

> wfh-research 共享包 · 协议版本 1.1 · 2026-11-13
> 执行者：`wfh-grill`。其他技能只引用本文件，不复制。
> 本协议自带全部规则，不依赖任何外部插件；matt 的 `grilling` / `grill-with-docs` 只作为设计来源，不要求安装。
> 默认树见 [盘问树](grilling_tree.md)；自检与失败模式见 [盘问自检](grilling_failures.md)。

---

## 0. 这份协议解决什么

把「一个模糊的研究想法」收敛成「一组用户确认过的决策」，并在收敛过程中即时留下三类记录：

| 产物 | 作用 | 写入时机 |
|---|---|---|
| `TERMS.md` | 构念的操作定义 | 术语一确定就写 |
| `decisions/MDR-*.md` | 过三门槛的方法决策 | 决策一过门槛就写 |
| `decisions/LEDGER.md` | 决策台账 | 确认门通过后写 |

它不生产论文内容，不替代文献综述，不替用户做研究判断。

### 0.1 与 ARS Socratic 的分工

| | ARS `deep-research` socratic | 本协议（`wfh-grill`） |
|---|---|---|
| 目的 | 让用户自己想明白（探索 / 学习） | 把决策问全、问快（收敛） |
| 节奏 | 一次 1–2 问，固定层序 | 一轮问完整个 frontier |
| 生成 | 非生成，不替用户提 RQ | 程序性 / 学科惯例可给建议；实质性不生成 |
| 落盘 | 结束时一次性产物 | 术语与 MDR 即时写 |
| 终止 | 收敛信号 / 轮数上限 | frontier 空 + 用户确认 |

用户还在「不知道要研究什么」时，先走 socratic 或 lit-review；用户已经想清楚、只差写作时，直接进 `wfh-spec`。

## 1. 三个基本概念

### 1.1 设计树（design tree）

- **节点** = 一个待定决策；**边** = 依赖：A 的答案会改变 B 的选项集合，则 B 依赖 A；**根** = 课题本身。
- 每个节点至少标注四件事：

  | 字段 | 取值 |
  |---|---|
  | 类别 | 程序性 / 学科惯例 / 实质性（见 `decision_classes.md`） |
  | 状态 | 待定 / 已定 / 已修订 / 不适用 |
  | 依赖 | 无，或上游节点 ID |
  | 事实需求 | 无，或需要查什么 |

- **已知不是决策。** 用户材料、工作区文件、常识里已有答案的节点，直接标「已定」，不提问。
- 课题不需要的节点标「不适用」，并在台账记一行理由。
- 树在对话中维护，不要求把整张图展示给用户；每轮开始前重算 frontier。

### 1.2 frontier

**frontier = 所有前置已定的待定节点。**

- 「前置已定」指：该节点的**选项集合**不受任何未定决策影响。
  - 反例：字数预算的选项取决于目标期刊；期刊未定时，字数预算不在 frontier。
  - 反例：研究设计的选项取决于证据来源和主张强度；两者未定时，研究设计不在 frontier。
- 同一轮内的问题必须**互不依赖**：任何一题的答案都不会改变同轮另一题的选项。
- 依赖尚未返回的事实的节点，不在本轮 frontier；等事实返回后再进。
- frontier 由判断得出，不需要真的画图；每轮显式检查一句：「这轮里有没有一题依赖另一题？」

### 1.3 轮（round）

- **一轮 = 一次问完整个 frontier，然后停下等回答。**
- 用户可按编号回答：「1 是，2 选 b，3 否，因为……」。不要要求用户复述问题。
- 回答后依次做四件事：
  1. 更新树：把回答落到节点上，标「已定」；
  2. 处理冲突：若答案推翻旧决策，按 §6 重开；
  3. 重算 frontier；
  4. 问下一轮。
- **轮次预算**：核心 8 题目标 ≤3 轮；加研究类型分支后目标 ≤4 轮。第 5 轮起，先在轮首报告 scope 过大，再问用户是否收窄，不默默继续。

## 2. 提问格式

### 2.1 可推荐题（程序性 / 学科惯例）

```markdown
❓ **Q2 — 目标期刊与文章类型**

你想投哪一类期刊？这决定字数、结构、图表上限和审稿预期。
（a）领域顶刊  （b）专业刊  （c）会议 / 快报  （d）还没定

➡️ **默认建议**：专业刊。理由：单篇实证论文在专业刊的篇幅与审稿预期内更容易讲完整；顶刊通常要求更强的因果识别或更大的样本。**可推翻**：换选项只需说明理由，不会被视为错误。
```

学科惯例题在建议前加标注：

```markdown
➡️ **惯例建议（学科惯例，不是事实）**：按中等效应量、power = .80、α = .05 估算，需要 N ≈ 200；考虑 20% 流失，招募 250。理由：这是教育研究面板调查的常见做法。偏离需要理由（如只做描述性分析可降低要求）。**可推翻**。
```

### 2.2 实质性题（不给建议）

```markdown
❓ **Q4 — 主张强度**

你打算主张因果、关联，还是描述？这决定研究设计能否支持结论，也决定审稿人会怎么攻击。
（a）因果  （b）关联  （c）描述

⛔ **这一题没有建议**：主张强度是论文的核心承诺，必须由你给出。我可以做的是：列出每种主张需要的最低证据，以及你当前材料能支持到哪一档；但不会替你选。
```

用户明确要求对实质性题给建议时，仍然不给：只列选项与代价，请用户自己给答案；用户仍不决定 → 标 `[UNRESOLVED]`，留待下游。

### 2.3 格式硬规则

1. 每题编号 + 标题；正文说清「这题决定什么、影响哪些下游产物」。
2. 可推荐题的「yes」必须等于接受建议；建议单独一行，以 `➡️` 开头。
3. 实质性题只列选项与代价，不出现倾向：
   - 不排序选项；
   - 不写「通常」「建议」「更好的做法」「主流是」；
   - 不说「如果是我」；
   - 不给默认值、加粗推荐或「供参考」式暗示。
4. 一题只问一个决策；复合题可拆子项，但同一题内的子项必须同轮可答，且各自标注类别。
5. 事实由系统查（见 §4），不问用户本可查到的事实。
6. 一轮只问本轮 frontier，不混入下一轮的问题。
7. 用户已经答过的，不重复问；把答案复述为「已定：……」，让用户有机会纠正。

### 2.4 「每题带默认建议」的准确含义

验收口径里的「每题带可推翻的默认建议」指**可推荐题**（程序性 / 学科惯例）。实质性题按三分法**必须没有建议**，给建议即为违规。

两者不矛盾：默认建议的作用是降低往返成本，不是替用户做研究判断。

## 3. 三分法与推荐策略

完整定义、判据、边界案例见 [决策三分法](decision_classes.md)。速查：

| 类别 | 例子 | 推荐策略 | 标注 |
|---|---|---|---|
| 程序性 | 期刊格式、字数、结构模板、引用风格、检索策略、图表数量 | ✅ 默认建议 + 理由 + 可推翻 | `类别：程序性` |
| 学科惯例 | 样本量惯例、报告规范、统计呈现格式、伦理流程 | ✅ 「惯例 + 建议」，说明是惯例不是事实 | `类别：学科惯例（惯例，不是事实）` |
| 实质性 | RQ、贡献声明、研究设计、机理归因、理论框架、结果解释、证伪条件、伦理立场、作者顺序、FINER 评分 | ❌ 不给建议 | `⛔ 这一题没有建议` |

规则：

- **分类存疑 → 按实质性处理**（不给建议），并在台账标「分类存疑」。
- 同一题内不同子项可分属不同类别：分别标注、分别处理，不因为整题「看起来程序性」就给实质性部分建议。
- 分类在**提问前**完成，不是事后补标。

## 4. 事实调查（facts）

### 4.1 什么算事实

- **期刊**：scope、文章类型、字数 / 图表上限、开放获取政策、投稿要求、AI 使用披露政策。
- **报告规范**：EQUATOR 网络中哪些指南适用（CONSORT / PRISMA / STROBE / ARRIVE / COREQ 等）。
- **学科惯例的量化部分**：样本量惯例、常用效应量、常用量表及其信效度。
- **仪器 / 方法**：可及性、检出限、分辨率、样品要求、测试标准。
- **用户自己的材料**：已有数据、之前论文、导师要求、机构模板（读工作区或用户给的文件）。

### 4.2 怎么查

1. 把事实需求拆成可独立回答的小问题，**并行**派 subagent（当前 harness 的 Agent / Task 机制）。
2. 每个 subagent 的指令包含：
   - 要回答的问题（一句话）；
   - 允许的来源范围（期刊官网 / 作者指南、EQUATOR、仪器手册、数据库、用户文件）；
   - 输出格式：结论 + 来源（URL / DOI / 文件名）+ 核验日期 + 置信度；
   - 查不到时的写法：`[待核验]` + 已查来源清单，不许猜。
3. **不阻塞本轮。** 事实在跑时，照常问不依赖它的问题；只有依赖它的问题等到下一轮。
4. 事实结果在对话内维护，不新建 `artifacts/` 文件；需要留痕时写进相关 MDR 的「证据与来源」或台账备注。

### 4.3 查不到怎么办

- 标 `[待核验]`，并写清「查了什么、为什么没查到」。
- 下游不得把 `[待核验]` 写成确定结论。
- 不编造引用、期刊要求、仪器参数或报告规范。
- 用户主动提供的事实可以采信，但标「用户提供，未核验」。

### 4.4 事实与决策分开

- 事实题包装成决策题问用户（「你想投的期刊字数是多少？」）→ 派 subagent 查，或标 `[待核验]`。
- 用记忆冒充来源（「据我所知该刊要求 8000 词」）→ 没有来源就是 `[待核验]`。
- 因为事实没回来就跳过依赖它的决策 → 正确做法是把它留在 frontier 之外，下一轮再问。

## 5. 反谄媚

### 5.1 连续接受推荐

**计数器**只对「可推荐题」计数：

| 用户回答 | 计数动作 |
|---|---|
| 原样接受（「是」「同意」「按建议」） | +1 |
| 修正（接受但改参数） | 清零 |
| 否决（换选项） | 清零 |
| 未答 / 跳过 | 不变 |
| 实质性题的回答 | 不变（它不是「接受推荐」） |
| 强制无建议题的自答 | 清零（这是独立判断的证据） |

- 计数达到 **3** 后，置一个「下一轮强制无建议」标记（在台账或轮次笔记里记下；本轮已发出的问题不改，因为本轮答案尚未返回）。下一轮的第一道可推荐题强制不给建议，题首写：

  > 反谄媚触发：你此前已连续 3 次以上接受建议，这一题请你自己给。

  该题答完后清除标记、计数清零，恢复推荐。
- 标记一旦置上，**本轮后续回答不会取消它**（即使计数后来因修正而清零）。
- 若下一轮开头几题是实质性题（本来就没有建议），不消耗这次强制；强制顺延到该轮第一道可推荐题。

### 5.2 整场 yes-rate

- `yes-rate = 接受推荐的题数 / 实际给出建议的可推荐题数`（强制无建议题不计入分母）。
- 可推荐题 ≥5 且 yes-rate > 80%：提示一次（下一轮开头；若已无下一轮，则在确认门前）：

  > 你可能在顺着我，而不是在做决定。要不要我列出每题被否决的代价？

- 只提示，不停止；用户可以选择继续。

### 5.3 三项健康检查

每轮结束时自检，不要求输出给用户，但发现异常要处理：

| 检查 | 异常信号 | 动作 |
|---|---|---|
| 持续认同 | 用户连续点头，不补充理由 | 触发 §5.1 |
| 回避冲突 | 用户推回时，我把问题软化了 | 重述原问题，不降级、不换更温和的版本 |
| 提前收敛 | frontier 未空，我却想总结收尾 | 撤回总结，继续问 |

- 用户明确说「就这样」「先到这」：尊重，但台账标「frontier 未完成」，并列出未问节点；不假装达成共识。
- 不表扬用户的答案（「很好的想法」「这个方向很有前景」）；只确认事实与后果。

## 6. 重开（reopen）

### 6.1 触发条件

- 新答案与已定节点冲突；
- 事实返回后，原决策的前提不成立；
- 用户主动改主意。

### 6.2 动作

1. **下一轮开头明说**：「Q2 的答案推翻了 D5（研究设计），我重开这一支。受影响：D8、D11。」
2. 受影响的下游节点状态改回「待定」，重新进入 frontier。
3. 台账原行**保留**，状态改 `已修订`，在理由后追加 `→ 由 D12 取代`；新决策用新 ID，不覆盖历史。
4. 已写的 `TERMS.md` / MDR 若受影响：更新文件，在「修订记录」追加一行。
5. 重开的节点在**下一轮**问，不在当前轮补问。

### 6.3 常见重开

- 换期刊层级 → 贡献框架可能要改（Q2 反噬 Q1）；
- 主张强度从关联改成因果 → 研究设计、样本、分析策略全部重开；
- 样本渠道不可行 → 证据来源与设计重开；
- 伦理审批不允许原设计 → 设计重开。

## 7. 即时落盘

### 7.1 TERMS.md

- **触发**：一个构念的操作定义、包含 / 排除边界在对话中确定。
- **动作**：立即按 `terms_template.md` 追加一行，状态 `待确认`。
- 只记有争议、项目特有、需要操作化的构念；教科书定义不记。
- 三个必要条件缺一不可：操作定义、包含、排除。缺任一 → 继续问，不落盘。
- 边界案例（「成绩好但缺勤算不算高参与」）是压力测试工具；问过就记在「边界案例」列。
- **术语澄清不占规划问题编号**：它随轮进行，不计入 8 题；若澄清结果改变依赖关系，照常重算 frontier。

### 7.2 MDR

- **触发**：一个决策**同时**满足三门槛（见 `mdr_template.md`）：
  1. 难以逆转；
  2. 没有上下文会令人意外；
  3. 真实权衡。
- **动作**：立即写 `decisions/MDR-0001-<slug>.md`，状态 `草稿`。
- 不满足三门槛的决策只进台账，不写 MDR。
- 编号四位递增，不复用、不重排、不删除；废弃时保留文件并写替代它的编号。

### 7.3 决策台账（LEDGER）

- 全程在**对话内**维护，不提前落盘。
- 每行字段：

  | 字段 | 说明 |
  |---|---|
  | ID | `D01`、`D02`…… |
  | 决策 | 一句话 |
  | 类别 | 程序性 / 学科惯例 / 实质性 / 分类存疑 |
  | 选择 | 用户确认的答案 |
  | 理由 | 用户的理由；若是接受建议，写「接受建议」+ 建议要点 |
  | 可逆性 | 高 / 中 / 低 |
  | 影响章节 | Method / Results / Discussion / Limitations / Response 等 |
  | 接受推荐 | 是 / 否 / —（实质性题或强制无建议题填 —） |
  | MDR | 编号或 — |
  | 状态 | 已确认 / 待确认 / 已修订 / 未决 / 不适用 |

- 台账是 `decisions/LEDGER.md` 的唯一来源；确认后按 flow_template §0 与 flow_details §8.5 同步 FLOW 的阶段、已确认决定索引、中文摘要和唯一下一步，不写未确认台账。
- 跨会话重开先读 `decisions/REOPEN-*.md`，按 classification、affected_decisions 重开对应分支；旧行标已修订，新决定用新 ID，包内追加处理日期与 accepted / rejected；受影响步骤交给规划重新确认。

## 8. 确认门

**frontier 空 ≠ 可以动笔。**

### 8.1 门的检查清单

- [ ] frontier 为空，或用户明确接受剩余未决项；
- [ ] 台账完整：每个节点都有行，含「不适用」与「未决」；
- [ ] 产物清单：`TERMS.md` 几行、MDR 几份、`[待核验]` 几项、`[UNRESOLVED]` 几项；
- [ ] 每条实质性决策都能看到用户的理由，而不是「AI 说这样好」；
- [ ] 证伪条件已有答案，或用户明确接受 `[UNRESOLVED]` 并在台账记录接受事实；
- [ ] FINER 五项已由用户评分，或明确标 `[UNRESOLVED]` 并在台账记录接受事实；
- [ ] 没有把 `[待核验]` 写成确定结论。

### 8.2 门的输出

按顺序输出：

1. **研究决定摘要**（完整覆盖每条决定的中文内容、理由和影响；内部字段不原样展示）；
2. **未决与待核验事项**（逐条说明作者要判断的内容与证据缺口；文件维护由系统负责）；
3. **一句提问**：

   > 这些研究决定、理由和未决事项是否就是我们的共同理解？确认后我会保存记录并整理研究方案；现在先等你确认。

4. **停下。** 不写 `BRIEF.md`、不写正文、不调用 ARS 生产技能。

### 8.3 确认的判定

- 算确认：明确的「是」「确认」「可以，就这样」，且没有提出修改。
- 不算确认：「差不多」「先这样吧」「你看着办」→ 追问「哪几行还需要改？」
- 用户确认后又改：台账标「已修订」，重新过门。

### 8.4 确认后的动作

1. 写 `decisions/LEDGER.md`（模板见 §8.5）；
2. `TERMS.md` 行状态 `待确认` → `已确认`；
3. MDR 状态 `草稿` → `已确认`；
4. 未决项标 `[UNRESOLVED]`，待核验标 `[待核验]`，留给下游；
5. 提示下一步：`/wfh-spec`（生成 `BRIEF.md`）。

## 9. 会话收尾

- 停在确认门，不自动进入 `wfh-spec`。
- 收尾消息包含：决策数、MDR 数、未决项、待核验项、建议下一步。
- 若用户要在 frontier 未空时结束：列出未问节点，标「未完成」，不假装达成共识。
- 不在收尾时「顺便」写 Brief、提纲或正文。
